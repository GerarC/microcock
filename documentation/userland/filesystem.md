# File system

The file system is not in the kernel. It is a set of Ring 3 servers that talk by IPC and shared memory, all with the same protocol: `ramfs` serves the files of the `initrd` (a ustar archive loaded as a data boot module, see [memory management](../core/memory_management.md)), `fat` serves a FAT32 volume of the disk (see [FAT32](fat32.md)), `ext` serves an ext2 volume (see [ext2](ext2.md)), and `vfs` is the one name clients use: it forwards each request to the server that owns the path. `ramfs` is read only; `fat` and `ext` can also create, write and delete files.

## Boot
1. The kernel keeps `initrd` as a data module and loads `ramfs` as a boot module; every other program is a file of the archive: under `drivers/` and `servers/` the programs of `userland/drivers/` and `userland/servers/`, under `bin/` the applications and the test programs, none with an `.elf` suffix.
2. `rs` asks `SYS_MODULE_INDEX` for the index of `initrd` (only a process with grant authority may ask), grants `ramfs` a `BOOT_MODULE` capability for that one module and sends it `CAPABILITY_GRANTED`.
3. `ramfs` opens the module, maps it read only and walks the tar headers once into an index of up to 64 entries (name, data offset, size, type). Requests that arrive before the grant are kept (up to 16) and answered afterwards.

## Protocol
Every request carries a request id in `arg0`; the reply (`FS_REPLY`) echoes it in `arg0` and carries the status in `arg1` and up to two values in `arg2` and `arg3`. A client accepts a reply only from the server pid and with its own id. The constants are in `shared/include/cock/abi/fs.hpp`.

| Message | Arguments | Reply values |
|---------|-----------|--------------|
| `FS_CONNECT` | none | id of the window |
| `FS_OPEN` | `arg1` path length, `arg2` flags (read only is 0) | handle |
| `FS_READ` | `arg1` handle, `arg2` offset, `arg3` length | bytes copied into the window (0 at the end of the file) |
| `FS_WRITE` | `arg1` handle, `arg2` offset, `arg3` length (the data is in the window) | bytes written |
| `FS_UNLINK` | `arg1` path length | none |
| `FS_MKDIR` | `arg1` path length | none |
| `FS_RMDIR` | `arg1` path length | none |
| `FS_RENAME` | `arg1` length of the old path (at the start of the window), `arg2` length of the new path (at byte 128 of the window) | none |
| `FS_LINK` | `arg1` length of the existing path (at the start of the window), `arg2` length of the new name (at byte 128 of the window) | none |
| `FS_STAT` | `arg1` handle | size, type |
| `FS_READDIR` | `arg1` handle of a directory, `arg2` index | name length, type (the name is in the window, ended by a zero) |
| `FS_CLOSE` | `arg1` handle | none |

`FS_OPEN` accepts a directory: `/` is the root and `docs` or `docs/` a subdirectory. `FS_READDIR` lists the direct children of a directory in archive order and answers `OUT_OF_RANGE` past the last one; on a regular file it answers `UNSUPPORTED`, as `FS_READ` does on a directory.

### Writing
Flags of `FS_OPEN` are a set: `OPEN_WRITE` (1), `OPEN_CREATE` (2) and `OPEN_TRUNCATE` (4). `CREATE` and `TRUNCATE` need `WRITE` (otherwise `BAD_REQUEST`); a bit outside the set is `UNSUPPORTED`. `CREATE` makes the file when the path does not exist and opens the existing one otherwise; `TRUNCATE` empties an existing file; only regular files can be opened for writing (a directory answers `UNSUPPORTED`).

- `FS_WRITE` needs a handle opened with `WRITE` (`READ_ONLY` otherwise). The offset must not be past the end of the file (`OUT_OF_RANGE`): a file grows by appending, there are no holes made by the server. A request is cut to the window and to the largest file size of the server; the reply carries the bytes written, which can be less than asked when the volume fills up (`NO_SPACE` only when nothing was written).
- `FS_UNLINK` deletes a regular file (a directory or a link answers `UNSUPPORTED`, a missing path `NOT_FOUND`).
- `FS_MKDIR` makes a directory (`EXISTS` when the name is taken, `NOT_FOUND` when the parent is missing or is not a directory). `FS_RMDIR` removes an empty directory (`NOT_EMPTY` otherwise, `UNSUPPORTED` for anything that is not a directory, the root cannot be removed). `FS_RENAME` moves a file or a directory inside one file system, to another directory if wanted: a file replaces a file and a directory replaces an empty directory (`NOT_EMPTY` when the target directory has entries, `EXISTS` for a file onto a directory or the reverse), and a name that differs only in case from the old one is renamed in place; `BAD_REQUEST` when a directory would move into itself, `CROSS_DEVICE` when the two paths belong to different mounts (the `vfs` answers that without asking a server). An entry that is open anywhere, directories included, answers `BUSY` to `FS_RMDIR` and `FS_RENAME`, and so does a rename onto a target that is open. `FS_LINK` makes a hard link to a regular file: `EXISTS` when the new name is taken, `UNSUPPORTED` for a directory or when the file system has no links (FAT), `BUSY` when the file is open, `NO_SPACE` at the link limit, `CROSS_DEVICE` across mounts. There are no symbolic links yet.
- **One writer, or many readers.** A file open for writing is exclusive: another open of the same file answers `BUSY`, and so does opening for writing a file that is open for reading, truncating it, or unlinking it. This keeps the copy of the size and block list that each handle holds from going stale. The check spans all sessions of the server, so it also covers clients that come through the `vfs`.
- A server that cannot write (`ramfs`, a volume on the whole-disk device, an ext2 volume with a journal, unknown read-only features, or not marked clean) answers `READ_ONLY` to `FS_WRITE`, `FS_UNLINK` and any open with write flags. The `vfs` passes the flags, the data and the statuses through unchanged.
- File times come from the CMOS clock: `fat` and `ext` ask the `rtc` server (the only holder of `io:0x70+2`) for the date and time when they create or change an entry. A server that cannot reach `rtc`, or gets a clock that answers nonsense, writes a fixed date (FAT) or a fixed mark (ext) instead. There is no time zone: the clock is taken as UTC.

File types: `REGULAR`, `DIRECTORY` and `SYMLINK` (only `ext` reports links; a link opens as its target).

Statuses: `OK`, `NOT_CONNECTED`, `BAD_REQUEST`, `NOT_FOUND`, `BAD_HANDLE`, `OUT_OF_RANGE`, `NO_SPACE`, `UNSUPPORTED`, `IO_ERROR` (the disk failed; the disk servers answer it), `READ_ONLY`, `BUSY`, `EXISTS` (the name is taken, also by something `resolve` could not open, such as a dangling link), `NOT_EMPTY`, `CROSS_DEVICE`.

### Window
Paths and data never travel in the message. On `FS_CONNECT` the **server** creates a one page shared memory object, shares it with the client with write access, maps it and replies with its id; the client maps it. The server owns the size, so a client cannot make it read past the end of a window. The path of `FS_OPEN` is copied out of the window once before it is used, and a leading `/` is accepted. The data of `FS_READ` is copied to the start of the window and a read never exceeds the window.

### Sessions and handles
The server keeps up to 8 sessions keyed by the badge of the handle the client holds (its process id), each with 16 handles. A handle is a number from 1, valid only in the session that opened it. A copy made by `fork` gets a session of its own (a window of its own) and a slot for each file of its parent under the same numbers, which share the file at the backend until each of them closes; this happens when `rs` sends `vfs` the `PM_FORKED` notice (`notify=fork`). A second `FS_CONNECT` from the same process resets its handles and returns the same window, unless it carries `CONNECT_KEEP_FILES` (a program that replaced its image with `exec`) or it is the first one of a copy made by `fork`: the files stay. The window is shared with the client again each time. When a client asks to connect and the table is full, the server asks `SYS_PROC_ALIVE` about every session, unmaps the window of each dead client, releases its shared memory object and frees the slot. A client that dies leaves its session until then. The process id carries a generation, so a recycled slot is never mistaken for the old client.

## The `vfs` server
`vfs` is spawned from the initrd by `rs` and needs no capabilities. Clients connect to it by the name `vfs` (`abi::fs::SERVER_NAME`); only `rs` talks to `ramfs` directly, because it has to read the manifest before `vfs` exists.

- **Mount table.** Read at start from `mounts.conf` in the initrd (through `ramfs`, by name, like `rs` reads the manifest; the parser is `shared/include/cock/abi/mounts.hpp`). One line per mount, a prefix and the name of the server: `/ ramfs`, `/fat fat`, `/ext ext`, `/mute mute`. Empty lines and lines that start with `#` are ignored. A prefix starts with `/`, has no trailing `/` and no empty component; there are at most 8 mounts, the prefixes are unique and `/` must be one of them. A bad file makes `vfs` print the line and the error and exit. The device a server uses is the argument of its line in the manifest (`arg=`), not part of the mount. A path is made absolute (a leading `/` is added when missing), the longest prefix that ends at a component boundary wins (`/fatx` belongs to `/`, not to `/fat`), the prefix is removed and the rest is sent to the server (`/fat` alone becomes `/`).
- **Proxy.** `vfs` is itself a client of each server, with its own window, which it connects to the first time the mount is used (a mount whose server is not running answers `NOT_FOUND`). The data of a read goes from the window of the server straight into the window of the client, one copy. Statuses from the server are passed on unchanged, so a client sees the same refusals whichever server owns the file.
- **Handles.** A handle is the slot number plus one in a table of 16 open files shared by all clients (each server allows 16 handles to `vfs`), and it is only valid for the client that opened it. When the table is full, or a client connects again, or a session slot is needed, `vfs` closes the files of dead clients (`SYS_PROC_ALIVE`) at the server and frees their sessions.
- **One request at a time.** While `vfs` waits for a server it keeps the requests that arrive in a queue of 16 and handles them afterwards, so another client is never lost.
- **A server that dies.** The clients wait for a reply with `SYS_IPC_RECV_TIMEOUT` (20 ms) and, each time it runs out, ask `SYS_PROC_ALIVE` about the server; when the server is gone the call fails instead of waiting forever. `vfs` then marks the mount as down, forgets the open files of that mount (their handles belonged to the dead server) and answers `NOT_CONNECTED`; the next request to that mount looks the server up again, so a server that was started again is used without restarting `vfs`. A reply wakes the waiting client at once; the client sleeps in the kernel between liveness checks and uses no CPU.
- **The root listing** (`/`) shows the entries of the file system mounted on `/` and then one directory for every mount whose prefix has a single component (`fat`, `ext`, `mute`). Mounts deeper than that are reachable by name only.
- **Not yet.** Changing the table needs a new `mounts.conf` in the initrd; no mount or unmount at run time.

## Programs from the initrd
`rs` is the first client. It reads `manifest.conf`, and for each program of the manifest it opens the file, reads it into an anonymous mapping through the window and calls `cock::user::spawn`, which builds the process with the `SYS_PROC_*` calls; see [the manifest](userland.md#the-manifest) and [task management](../core/task_management.md#spawn). `fsclient` is a small client that the manifest runs ten times to exercise the release of sessions; it goes through `vfs`, so the release is exercised there too. `mute` is a server that reads one message and exits without answering, and `muteclient` checks that a request to it through `vfs` fails instead of hanging, that the file system still answers afterwards, and that a direct client of the dead server also fails.

## Client library
`userland/lib/include/cock/user/fs.hpp` offers `cock::user::fs::Client` with `connect(name)` (the default is `vfs`), `open` (with optional flags), `read`, `write`, `unlink`, `mkdir`, `rmdir`, `rename`, `readdir`, `stat`, `close`, `lastStatus()` (the status of the last call, `NOT_CONNECTED` when the call did not go through) and the raw `call`. `userland/lib/include/cock/user/file_server.hpp` is the whole server side for `fat` and `ext`: a backend says how to resolve a path, read and write bytes, create, truncate and unlink a file and list a directory, and the template does the sessions, handles, windows, validation and replies. A server that is a client of another sets `onForeign`, a function that receives the messages that arrive while it waits for a reply; `vfs` queues them. A reply is awaited with `receiveReply` (`userland/lib/include/cock/user/reply.hpp`), which waits with `SYS_IPC_RECV_TIMEOUT` and gives up when the server is no longer alive. `userland/lib/include/cock/user/session.hpp` has the session helpers the four servers share (`findSession`, `freeSession`, `openSession`, `releaseSession`). A program that uses it lists `string/memcpy.cpp` and `string/strlen.cpp` in `LIBC_SRCS`.

## Tests
`probe` checks that the file of the initrd reads back whole and in pieces (`initrdFileReads`, which also prints it), that `fileServerListsDirectories` lists the root and a subdirectory and reads a nested file, that the server refuses bad paths, handles, offsets, flags and lengths (`fileServerRefusesBadRequests`), and that a program without authority cannot call `SYS_MODULE_INDEX` (`moduleIndexIsDenied`). The success path of `SYS_MODULE_INDEX` runs at every boot: `rs` needs it to grant `ramfs` the `initrd`, and the end to end test requires the line `rs: initrd is boot module`. `probe` also reads the manifest through the client, parses it and checks that its own entry has no grants (`manifestMatchesTheBoot`). The test also requires ten `fsclient: ok` lines, which only happen if dead sessions are released. `test/userland/lib/include/cock/user/write_check.hpp` is the write check that `fatclient` and `extclient` run in a scratch directory of their volume (create and read back, a large file written in windows, an unaligned overwrite and an append, a write past the end, the exclusivity rules, truncate, delete, the refusals and the listing, then directories made, moved, renamed and removed, long names, alias collisions, renames that replace a name or only change its case, and hard links); the end to end script then runs `fsck.fat -n` and `e2fsck -fn` on the partitions and reads the surviving file back from the host.
