# fork

`SYS_PROC_FORK` is the kernel part of `fork`, with the same shape as [exec](exec.md): the program asks `pm` (`Op::FORK`), `pm` asks the kernel for the copy, and `pm` answers both sides. Does it have to live in the kernel? The copy of the address space and of a saved thread context cannot leave it, and the page fault of the first write is the kernel's; everything else, the table of processes, who may fork and what each side is told, is in `pm`.

The caller needs the `SPAWN` capability, and the target must be the main thread of another user process that waits for the reply of a call the caller is serving; that is the same consent as for `exec` (`serves_main_thread`), and it means the target is not running, so its address space is not the active one and its saved context is complete. Everything that can fail is checked before anything is created: the caller can take one more exit notice, a process id is free, the derivation tree has room for the copies of the capabilities, every shared object the target holds has a free holder slot, and the page tables of the copy fit in memory above the kernel reserve. Then:

1. `VirtualMemoryManager::cloneAddressSpace` copies the page tables and shares the frames copy on write ([copy on write](../memory/copy_on_write.md)).
2. A new `Process` takes that address space, the user limit, the name, the table of regions, the page quota in use and the capability types a message may give (`Process::copyImageFrom`). A shared object mapped by the target is counted as mapped once more, and the child becomes a holder of it with the access of the parent. The quota of the child starts equal to the parent's: nothing is copied yet, but the pages are as many as the parent's.
3. `Thread::createClone` makes the only thread of the child: its own kernel stack and a copy of the saved context of the target (`hal::clone_thread_context`), so it resumes at the same instruction, on the same user stack address, inside the same call to `pm`. `SyncIpc::writeReply` puts the four words that `pm` supplied into that context as the answer to the call, so the child sees `OK` and a process id of zero, while the parent gets its own answer from `pm`. The other threads of the parent do not exist in the child.
4. The child is a child of the caller (`pm`), which gets its exit notice, and it has no service label. It gets the capabilities of the parent that are inheritable ([capabilities](../capabilities.md#inheritance-by-fork)) and nothing else.
5. The child is queued; the target stays as it was, still waiting for the reply of `pm`.

A failure in the middle undoes what was done: the process is deleted, which returns the tables and the references it took, and no process id or exit notice stays reserved. A write that needs a frame when none is free (the copies are made at the writes) kills the thread that wrote, like any fault; `fork` does not reserve those frames.
